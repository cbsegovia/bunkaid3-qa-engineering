# ADR-0001: Adopt PBI-as-cache tiering and ATS-primary traceability cascade

## Context

`.context/PBI/` is currently a fully committed, `[SYNC]`-tagged mirror of Jira content (630
tracked files as of this writing), regenerated by `scripts/sync-jira-issues.ts`. Two AI
sessions re-syncing the same Epic/Story at different times produce conflicting commits of
generated text, because the "source of truth is Jira, the file is a read-only cache" claim
in current doctrine is not backed by actual git-ignore policy — the cache is tracked, so it
participates in merge/diff/commit history as if it were authored content.

Separately, current doctrine's traceability language treats ATP/ATR Jira-field/comment links
as carrying Xray coverage weight, without distinguishing them from Xray's actual
membership-based coverage panel. Live verification against real Xray instances (per the
upstream `agentic-qa-boilerplate` architecture release) found that ATP/ATR container links
are administrative traceability only — they do not fill Xray's coverage panel. What fills it
is either (a) a Test Case's membership in an ATS (a Story-level artifact grouping all test
cases) with a Jira link back to the Story, or (b) a direct Test→Story link. This is a
correction to this repo's implicit prior assumption, not a request for a brand-new pattern.

## Decision

1. **PBI-as-cache tiering**: `.context/PBI/` generated content is designated `[SYNC]`-tier
   and MUST NOT be git-tracked going forward. Recovery is via a (not-yet-implemented)
   `bun run context:hydrate` entry point, documented as a named future capability rather than
   promised as working today. `[COMMIT]`-tier (README/templates/test-specs) and `[LOCAL]`-tier
   (session notes, evidence) distinctions are adopted as vocabulary now; their folder-level
   application inside `.context/PBI/` is deferred to the `scripts/sync-jira-issues.ts` rewrite.
2. **Traceability cascade correction**: CLAUDE.md's traceability doctrine is corrected to state
   that TC→ATS→Story (membership + link) and TC→Story (direct) are the links that count toward
   Xray coverage; TC→ATP→Story is administrative-only. ATS is adopted as a new mandatory
   Story-level artifact in future Stage 1 planning (propagation to `/sprint-testing` /
   `/test-documentation` SKILL.md files is a follow-up, not part of this ADR's binding scope).

## Consequences

**Positive:**
- Eliminates the two-sessions-conflicting-commits failure mode for generated PBI content.
- Corrects a traceability doctrine claim that was silently wrong relative to how Xray's
  coverage panel actually works — prevents future QA sessions from reporting false coverage.
- Vocabulary (`[SYNC]`/`[COMMIT]`/`[LOCAL]`, ATS) aligns this repo with the upstream boilerplate,
  easing future `/framework-development` syncs against it.

**Negative / trade-off:**
- Untracking 630 files is a one-time, hard-to-fully-reverse git-history event (the files remain
  recoverable from history, but the "committed cache" convenience — grep-across-tracked-files,
  no separate hydrate step — is lost going forward). Anyone who relied on `git log` /
  `git blame` over `.context/PBI/` content loses that going forward for new content.
- Until `context:hydrate` is actually implemented (blocked on this session having no working
  Xray credential path validated — see prior finding that the automation account has no
  workspace access), a developer with a clean clone has NO local PBI cache at all until a
  manual `bun run jira:sync-issues pull` is run. This is a real workflow regression until the
  hydrate command exists.
- ATS becomes a new mandatory artifact with no automation support yet (no `link create`, no
  `plan add-set`/`exec add-set` CLI) — Stage 1 planning that tries to honor "ATS mandatory"
  today would have to create/link it by hand via `acli`/`xray-cli` primitives that don't yet
  have a purpose-built command.

## Alternatives considered

- **Keep `.context/PBI/` committed, do nothing.** Rejected — the two-sessions-conflict failure
  mode is real and already observed as a doctrine-level concern; deferring indefinitely just
  accumulates more tracked generated files (630 today, growing).
- **Full big-bang adoption including Xray CLI additions.** Rejected for this ADR's scope —
  blocked on missing Xray credentials in this environment; would also require implementing
  ~3370 lines of sync-script changes without the ability to validate against a real instance.
- **Correct the traceability language without touching the cache-tier policy.** Considered as a
  smaller, doctrine-only-and-safer version of this ADR. Rejected as the sole action because the
  task explicitly required a cache-tier POLICY decision, and `kata-invariants.md` §10.1 already
  grants framework-development that authority — deferring it further would just re-litigate the
  same question next session with no new information.

## Gate check (adr-doctrine.md §1)

- **Gate 1 — architectural?** Yes. Both decisions are cross-cutting test-suite/process concerns
  (repo cache structure; traceability model), not ticket-local.
- **Gate 2 — hard to reverse?** Yes. Untracking 630 files and re-pointing doctrine that every
  `/sprint-testing` and `/test-documentation` session reads is exactly the kind of decision that
  requires coordinated re-work to reverse.
- Both gates pass → ADR is warranted.
